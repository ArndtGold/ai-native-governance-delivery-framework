## Solution Overview

Realize the approved two-column document overview through the existing undertaking/read experience and a bounded additive Core descriptive projection. The first column groups document name, icon and short state text; the second has one contextual draft/approved/current-document reading action. There is no inline expansion or separate approval destination. Existing document reading receives the same authoritative description, original approval evidence and applicable authoring findings.

Core retains approval/source and authoring authority. Extend cockpit.js with document-state projection driven by existing approval proof and authoring result owners. Refactor existing proof code only to expose its per-gate result while preserving the existing aggregate validator's exact behaviour. Do not implement a competing evaluator or extract positive state from prose. An ephemeral check-result slot in the existing per-view reader can survive same-Run document/return navigation only after full current identity revalidation; it is not a persistent report store or new session service. Existing request/snapshot/selector/teardown owners remain intact.

This is design, not implemented behaviour, test success, human approval or QA. The PRD remains the sole product source.

## Architecture Decisions

- SDD-001: Use one two-column document presentation and a versioned descriptive state record per registered gate document; rationale: compact rows and state facts must retain one meaning across widths/read surfaces; consequence: WorkStep consumes a presentational list with stable logical registration keys and existing resource actions, while Core projects state without changing Resource.status.
- SDD-002: Reuse the existing canonical approval proof through a per-gate extraction preserving aggregate behaviour; rationale: a saved approved row and current path alone do not bind the actual readable bytes; consequence: confirmed wording requires valid existing proof plus captured raw identity, otherwise preserve original approval and expose uncertainty.
- SDD-003: Reuse authoring results with Core-only diagnostic interpretation and one identity-checked ephemeral reader slot; rationale: checking is deliberate and current-gate bounded, while opening its document must retain only applicable findings; consequence: no bulk checking or durable result store, no stale resurrection, and technical failures remain separate from concrete authoring defects.
- SDD-004: Reuse existing large document reader, expansion and logical focus return with scoped responsive rows; rationale: one document action must have a clear destination and explain its state; consequence: no approval reading route, no expanding list entries, safe plain context/original text and existing close/back behaviour.
- SDD-005: Add validated optional read facts through existing MCP/HTTP operations while preserving selection, freshness and no-write boundaries; rationale: old readers and servers coexist and new descriptive facts cannot gain authority from malformed or absent data; consequence: old absence is unconfirmed, malformed present facts fail validation, exact snapshot/resource/content associations are enforced and no new selector/writer is introduced.
- SDD-006: Reassess retained code/tests against renewed sources and qualify protected incremental evidence across Core, protocol and built visible readers; rationale: previous inline results do not prove new semantics or native behaviour; consequence: capture a new scoped baseline, preserve history/foreign sources, review actual diff and report native observations separately without implicit installation.

### SDD-001 — Document list and descriptive record

Replace the old in-progress DocumentedApprovals component with a small internal RunDocuments presentation under WorkStep. It lists actual registered user-gate document types UR, PRD, SD, TP, QA and UAT only when registered. Existing non-gate analytical/source lists stay separate. Each distinct (Run, type, registered_reference) is one entry, using that logical key across width changes; multiple references of one type are distinguishable. Do not scan filesystem or synthesize unregistered document actions. Count entries, including explicit missing/blocked registered entries; label Dokumente. Missing source feedback can occupy the action cell without a working link.

Use a shared semantic list/grid with two labelled groups, scoped container reflow and existing spacing/target sizes. One DOM, natural wrapping and no sticky/animated/virtualized list are needed. No native details/summary inside overview entries; existing section or reader provenance disclosures are independent. Current Resource still flows unchanged through onOpen with origin document:<resource_id>. Existing App return-source matching already resolves type/reference and maps the refreshed opaque ID back to the origin prefix.

Add optional Detail.document_states: an array of version-1 non-authorizing records for these actual resources. Each record contains schema_version '1', resource_id, run_id, revision_id, type, registered_reference, source_state (available/missing/blocked/unsupported/unavailable), content_digest (full raw unprefixed SHA-256 or null), state (approved/draft/draft_checked/revision_required/check_unavailable/approval_unconfirmed/unavailable), version_kind (approved/draft/current/unavailable), reason (code or null), recorded_approval (status and unchanged original evidence or null), check (applicable matching descriptor/report information or null), authorizes false. Do not expose an independently verified person/time/signature unless existing structured evidence genuinely supports it; with current inputs state explicitly unavailable in reading context.

The envelope supplies target and snapshot. All records tie to actual same-Run registrations and the current Run revision; opaque IDs belong to that capture only. Read safe bounded bytes from the existing capture to determine availability/raw digest, never execute content. Gate documents beyond existing preview/read bounds are unsupported/unavailable, not certified. If the total descriptive addition exceeds 256 KiB, return the existing bounded resource_limit uncertainty rather than truncate, invent state or keep a positive incomplete projection. Existing capture/file/response/time limits still apply. No further dependencies are followed by the overview beyond current registered gate files and existing canonical proof files.

New records are computed in the Core reader once per captured detail/read result and updated after a deliberate draft check. Existing selectedDocument returns the fresh Detail and DocumentData with the same matching record; DocumentData.document_state is optional and must match the corresponding Detail record. A freshly read document's raw content_digest must equal its record's available digest. No document-state facts become registration, control, approval or permission.

### SDD-002 — One proof owner, actual version identity

Refactor the existing per-approved-gate body of exactApprovedArtefacts into an internal exported descriptive helper in artefact-binding-proof.js, e.g. inspectApprovedArtefact(root, control, gate, options). The aggregate validator delegates to that same helper and retains its existing all-approved/legacy/historical/target and proof checks exactly. No policy or acceptance condition is weakened. The descriptive helper reports confirmed false with a bounded reason when unsupported/unapproved/missing/malformed/foreign/mismatched; confirmed true requires all existing applicable receipt, prepared presentation, canonical/raw file digest and required source-binding checks. Existing run/source seal and canonical integrity are prerequisites for claiming current approval in cockpit projection.

For supported actually approved gates, additionally associate helper result with the actual same-Run registered gate path and the raw bytes captured for the readable resource. A canonical normalized digest alone cannot certify changed raw bytes. The existing presentation raw digest and read-document raw digest establish the exact readable correspondence. Gate types lacking existing document approval proof (including UAT without a canonical artefact proof) remain unconfirmed; do not certify a file using the aggregate validator's UAT omission. Unrelated positive records cannot bypass a damaged current Run; invalid integrity is uncertainty. Current permission to work remains the separately existing control assessment.

With positive proof the state is approved, version_kind approved and the appropriate contextual approved-document action is shown. With any earlier recorded approved fact but unconfirmed version/proof, return approval_unconfirmed/version_kind current when safely readable, retaining unchanged original approval evidence. No guessed Entwurf replacement. With canonically unapproved draft artefact, version_kind draft and its check state apply. Conflicting/unsupported original status or invalid source cannot be guessed from prose. Absent approval evidence is an explicit limitation, not a reconstructed archive. No historic document retrieval or new signing identity is introduced.

### SDD-003 — Check applicability and finding continuity

Existing projectArtifactReadiness remains the sole supported UR/PRD/SD/TP authoring check. Preserve current gate, lifecycle, target/Run/revision, source containment, integrity and deliberate invocation restrictions. No overview-triggered calls, new general check selector or check of approved/unsupported documents. Existing standalone inspect and cockpit check remain equivalent original authoring reports.

Share a small descriptive classification helper in the existing authoring/projection owner rather than duplicating validation in App. Passed means the existing ready report for the matching descriptor. Content defects are the existing explicit authoring diagnostics; additionally an artifact_gate_not_ready report can describe concrete current authoring findings only if its blocking_reason is one of the existing UR requirements/PRD decisions/SD decisions/SD or TP traceability readiness codes and its matching structured readiness_details contains actual open items. Preserve original report and gate block. Project those original code/message/open-item facts as findings; do not parse English messages, treat missing data as a defect or turn other gate/prerequisite/integrity/transport codes into corrections. Update the existing Core draft display using this same descriptive classification so the document row, document view and adjacent DraftCheck cannot disagree. DraftCheck may display the projected concrete findings while retaining the full original report for provenance. The authoring rules/gate decision remain unchanged.

Keep at most one successful captured authoring result (including applicable concrete corrections) in the existing per-view Core reader, bound to target, Run, gate, revision, canonical path/digest and full raw draft digest. Maximum serialized slot size 256 KiB; over limit gives existing resource_limit/unavailable feedback with no partial report. It contains check evidence, not document bytes or durable registration. Store only after current captured/publication identity succeeds. Same-Run run/document/context navigation may reattach it to new opaque IDs only after a fresh capture confirms all identities, source integrity, lifecycle/current gate and matching raw bytes. Publish it in the new current snapshot; never reuse its old resource/snapshot selectors. This continuity explains findings in the opened document and restores the meaningful state on return.

Explicit snapshot/reload, overview or another Run, missing/changed source or revision, failed capture, stale/source_changed observation and reader/session/worker teardown clear the slot. Request arguments rejected before capture do not disturb legitimate existing state; existing invalid-selector guarantee stays intact. New navigation cannot recover a rejected/failed capture's old slot. No result is shared between per-view readers or persisted to control/browser storage. A new explicit check replaces the old slot only with a fully applicable response. In-flight/busy/retry feedback stays existing request-owned transient presentation and must not forge a new Core checked/defective result. After reload the draft can be unchecked again, never automatically checked.

## AGDF Approval Summary (de; source=en)

- Lösung: Zwei kompakte Spalten zeigen Dokument, Icon/Statustext und einen passenden Leselink. Die vorhandene große Dokumentansicht enthält die zugehörigen Prüfbefunde und ursprünglichen Freigabeangaben. Keine aufklappbaren Listeneinträge und kein eigener Freigabelink.
- Zuständigkeit: Core liefert zusätzliche beschreibende Angaben pro registriertem Dokument. Die bestehenden Freigabe-, Quellen- und Entwurfsprüfer bleiben die einzige fachliche Autorität; die App zeigt deren validierte Ergebnisse an. Registriert bleibt als Ressourcenstatus von Freigegeben getrennt.
- Versionsbestätigung: Die bestehende Belegprüfung wird pro Gate wiederverwendbar gemacht; ihre bisherige Gesamtprüfung bleibt unverändert. Freigegeben verlangt passende Präsentations-/Freigabebelege, gültige Quellenintegrität und Übereinstimmung mit den tatsächlich gelesenen Dokumentbytes. Fehlende, geänderte oder ungültige Zuordnung bleibt ausdrücklich unbestätigt; keine neue Archiv- oder Freigabehoheit.
- Entwurfsprüfung: Nur der unterstützte aktuelle Entwurf wird bewusst geprüft. Konkrete passende Autorenbefunde ergeben Überarbeitung nötig, bestandene Autorenprüfung ergibt Entwurf geprüft. Technische oder andere Gate-Fehler bleiben Nichtverfügbarkeit. Ein einzelner begrenzter Prüfbefund darf beim Öffnen und Zurückkehren nur nach erneuter Quellen-/Revisionsprüfung erhalten bleiben; Neuladen, Quellenwechsel oder Sitzungsende löschen diesen temporären Stand. Keine Sammelprüfung und keine dauerhafte neue Ablage.
- Lesen und Bedienung: Bestehende Dokumentnavigation, Vergrößern, Schließen, Tastaturfokus und Quellen-/Fehlerbehandlung werden wiederverwendet. Dieselben Zeilen ordnen sich schmal/breit um, ohne doppelte Ansichten. Icon plus Text und eindeutige Aktionen bleiben verständlich; fehlende Herkunftsangaben werden benannt.
- Kompatibilität: Bestehende MCP-Aufrufe und Browser-Routen bleiben gleich. Neue Angaben sind optional und begrenzt; alte Server ohne diese Angaben bleiben lesbar und bestätigen keine unbekannte Freigabe. Vorhandene neue Angaben müssen zu Run, Revision, Ressource und Dokumentfingerabdruck passen; fehlerhafte oder fremde Antworten werden abgewiesen. Keine neuen Writer, beliebigen Dateipfade oder App-Auswertung.
- Nachweise und Risiken: Der erneuerte TP muss unveränderte Core-Belegprüfungen, tatsächliche Dokumentbytes, alle Prüf-/Fehlerzustände, temporäre Befundübernahme und deren Entwertung, MCP-/Browser-Kompatibilität, Tastatur/Scrollen und unveränderte Kontrollquellen prüfen. Frühere Inline-Tests gelten nicht als Erfüllung. Native Beobachtung wird getrennt berichtet; Installation, Veröffentlichung und Git-Aktionen sind nicht Bestandteil.
