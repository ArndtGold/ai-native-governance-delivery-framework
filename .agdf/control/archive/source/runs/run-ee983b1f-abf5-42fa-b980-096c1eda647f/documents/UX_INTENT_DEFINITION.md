# UX Intent Definition: One Current Run Model

- decision: ready
- blocking_reason: none
- primary_user_intent: Find a planned requirement or a started Run and understand its actual documents, current state and permissible next action without choosing between old and new storage models.
- success_signal: The same planned item/Run is identifiable across CLI/MCP and passive Cockpit; a started Run's documents and required history are accessible from its single folder; unsupported old stores are clearly identified without an automatic conversion/reset.
- primary_decision_or_action: Inspect the requirement/current Run, then deliberately perform the next existing authorized action. Planning does not start a Run or approve a gate; viewing never changes control.
- working_modes: UR-only planning; current Run inspection/decision; unsupported existing store; temporarily unavailable observation.
- effective_state_by_mode: Planning has an unapproved UR and explicit handoff readiness. Run inspection has current lifecycle/gate/revision and exactly bound material. An unsupported store has no interpretable current Run state under the new runtime. A failed/stale read has no freshly confirmed state.
- visible_state_types: Planned requirement, active Run, completed/ended current-format Run, current decision material, unavailable/stale observation, unsupported store/format. Do not relabel unsupported historical material as a current empty or completed inventory.
- effective_state_authority_by_mode: Existing planning/Run command and evaluation owners determine current state. Unsupported-store status is the outcome of validation, not a guessed legacy parser. Observation freshness is distinct from stored approval status. A deliberate exact user response remains the decision authority.
- primary_state_presentation_owner_by_mode: CLI/MCP project their canonical result and concrete next action; Cockpit projects the same state read-only. The currently used surface is the primary presentation, not a second state authority.
- activation_paths: Open a confirmed project, select a planned UR or exact Run, deliberately refresh observation, and explicitly request the existing handoff/record/approval operation. No legacy-view switch, implicit fallback or mode auto-selection remains.
- blockers: Unsupported control/Run format explains that this development model is no longer supported, with no migration offer. Missing/corrupt current data is a distinct blocker and must not be described as an unsupported old format or silently initialized. Stale material/revision requires refresh and fresh presentation; uncertainty after a write requires original-operation inspection.
- recovery_paths: For an old store, leave its bytes unchanged and use a separately and deliberately initialized fresh project/control location; this is guidance, not a destructive reset button. For recoverable read failure expose explicit refresh/retry. For interrupted current-format operations retain original identity and supported recovery; a timeout alone does not authorize replay with a new UUID. On changed decision material, present the current version and obtain a new deliberate response.
- relevant_state_transitions: Planned UR -> explicit handoff -> unapproved current Run. Current Run -> exact material presentation -> deliberate gate decision -> next existing step. Valid read -> stale/unavailable -> explicit refresh -> fresh observation. Unsupported store -> unchanged blocked observation; only explicit fresh setup at a safe location makes a new current store. Current operation interrupted -> known pending/unknown result -> exact operation inspection/recovery -> confirmed result.
- proposed_prd_acceptance_criteria: AC-001 one supported initialized model; AC-002 UR-only planning and explicit handoff; AC-003 complete single Run folder; AC-004 canonical metadata ownership/derived views; AC-005 old-store rejection without mutation; AC-006 one current Cockpit/CLI/MCP inventory without legacy mode; AC-007 exact decision-version semantics; AC-008 current-operation recovery/idempotency/concurrency; AC-009 aligned generated assets/docs/tests and bounded native evidence; AC-010 explicit governing-Run/development-data boundary.
- open_product_questions: none affecting the approved direction. PRD resolves these proposed criteria; SD owns exact subfolders, schema identifiers, implementation and self-hosting mechanics; TP owns scenario/evidence mapping.
- affected_outputs: PRD UX, working-mode/state, blocker/recovery/transition sections and acceptance criteria; later SD/TP mappings. This analysis creates no parallel product requirement authority.
- evidence: Approved UR digest sha256:3d8f1db643d8851719f9367e025d25f17b8643b3f2c96adafdcbf6995a833ac6; recorded BROWNFIELD_REVIEW.md digest sha256:a174d50b7acdd190f25fc045313178ac3fa9720360bc7cd77c0f38ede28b2ce5; observed cockpit-contract.js runs/legacy selector, cockpit.js projection and Overview.tsx split; existing planned-handoff and operation/approval owners. This is a written source-based scenario analysis, not observed user behavior or a delivered UI.
- missing_evidence: Actual implemented UI/CLI/MCP behavior, visible recovery and new-format host results are future test obligations. No preview was requested by UR (Preview requirement: none), so no mockup or interactive prototype is imposed. No native session or human UX observation has been performed.
