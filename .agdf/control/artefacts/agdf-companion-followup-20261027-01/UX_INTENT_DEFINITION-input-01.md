## 2. Intent And Success

- primary_user_intent: While AGDF delivery runs in Claude Code, know without asking and without watching the panel that the run of this session is being built, is waiting for an approval or is blocked, and see where it stands on the path its mode actually has.
- success_signal: With the companion switched on, the user notices a switch of the shown run to "waiting for approval" or "blocked" within one refresh through a single toast, reads the run's gate and state from the status line with the panel closed, and sees during Brownfield Analysis, CD+Tests and CR that the run is being built; a quick-task or verified-change run never shows gates it does not have.
- primary_decision_or_action: Switch the companion on or off (unchanged `/agdf-companion`); secondarily switch toasts and their sound on or off. The companion offers no decision on the run itself: approvals stay with the presented version in chat.

## 3. Working Modes And State

- working_modes: (1) off — no panel, no toast, no status line; (2) on, pane shown — panel, toasts and status line; (3) on, pane closed by the person for this session — toasts and status line continue, panel hidden until `/agdf-companion` brings it back; (4) on, terminal surface — text fallback in the pane, status line under the prompt, toasts on the notification line; (5) on, no run assigned or status unreadable — neutral panel and a neutral status line, no toasts. The run-dependent presentation within modes 2 to 4 depends on the run's path: structured (`structured_delivery`, `structured_slice`), verified change, quick task, block or undecided.
- effective_state_by_mode: Run-derived state, by precedence: fertig (lifecycle completed); blockiert (revise, block, blocked or decline, as today); wartet auf Freigabe (a pending gate approval or decision, as today); **baut** (new: a structured run whose current gate is Brownfield Analysis, CD+Tests or CR and that is neither blocked nor waiting); läuft (any other in-progress run). While a main-loop turn is active the panel shows läuft as today, except that a run in a build phase shows baut. The status line and the toast follow the run-derived state only, never the turn overlay, so a turn never flips them. The gate bar shows the path of the run's mode: structured `UR PRD SD TP CD+Tests QA UAT OR`, verified change `UR Verified Change OR`, quick task `UR Compact Delivery`, block `UR Block`, undecided `UR`; done, current and open marks agree with the status card, and the CD+Tests mark is current in the build phases and done from QA on.
- visible_state_types: Existing types stay (figure, state label, reason, gate bar, run identity, origin, objective, next step, read time, stepping, retry, still pose). New: the build figure (hammer and stacking bricks in the accessory region, a still pose without motion and the terminal face `(o_o) ⚒`); the label "baut" / "building" with the reason "In Arbeit: {gate title}" / "In progress: {gate title}" (gate titles from the AGDF locale packs, for example "Implementierung und Tests"); the CD+Tests mark; mode paths; a toast; a status-line entry; two switches "Meldung aus/an" and "Ton an/aus" (en "Notices off/on", "Sound on/off"). Hidden: an objective that is a template placeholder (no objective line instead of "Describe the trustworthy outcome.").
- effective_state_authority_by_mode: The run state is owned by AGDF control (`RUN_STATE.md` written by the canonical writers); the companion never decides or changes it. Whether a turn is active is owned by the Claude host. The on/off choice, the still pose, the toast and sound switches and the remembered selection are owned by the user. The mode path is owned by the run's Mode/Slice Decision as the status card reads it. The display language is owned by the AGDF chat language where control exists, else by the user's Claude language setting.
- primary_state_presentation_owner_by_mode: The side panel remains the primary presentation of the companion state on the desktop and the text fallback in the terminal pane. The status line is a secondary, glanceable presentation of the same run-derived state; the toast is a transient notice of a transition. The authoritative gate presentation and approvals stay with the AGDF status card and approval cards in chat; neither the toast nor the status line asks for or offers an approval.

## 4. Activation, Blockers, Recovery And Transitions

- activation_paths: Unchanged: `/agdf-companion` switches the companion on (pane, status line and toasts) and off (all three); a person's close of the pane hides only the pane for the session. Toasts are on and their sound is off by default (owner decision 2026-10-27); the panel offers "Meldung aus/an" and "Ton an/aus" in a second button row below the existing one; both choices persist across sessions with the existing choices. The sound plays only together with a toast. The brand reads "AGDF Companion" in every language (owner decision 2026-10-27); German sentences keep the name unchanged, for example "AGDF Companion eingeschaltet."
- blockers: (1) No AGDF control in the project: the panel says so as today, the status line reads "AGDF · bereit" / "AGDF · idle", no toast. (2) Unreadable run state: the panel shows the reason with a retry as today; the status line reads "AGDF · nicht lesbar" / "AGDF · unreadable"; no toast. (3) The host draws no toast, status line or sound (for example a terminal without a player): nothing else changes and no error is shown; the live test reports what the host does. (4) Incompatible host or mod API change: the companion stays unavailable; AGDF control functions keep working (unchanged failure isolation).
- recovery_paths: Retry ("Neu lesen") re-reads at once and updates panel and status line. A transient read failure keeps the last good state (marked stale in the panel) and raises no toast. `/agdf-companion` brings a hidden pane back. Switching the companion off clears the status line; switching it on starts a fresh baseline without a toast for the state found.
- relevant_state_transitions: Toast triggers: the shown run's run-derived state enters wartet auf Freigabe or blockiert from any other state, or stays in one of them while the gate or decision changes (for example a pending PRD approval followed by a pending SD approval between two reads). No toast for: the first successful read after switching on or after session start (baseline); a change of the shown run through assignment or stepping (new baseline); repeated reads of the same run, state, gate and decision; the turn overlay; a transient read failure; the companion being off. Status-line updates: on every applied read and on switching on or off. Gate-bar marks: TP done → CD+Tests current when the run enters Brownfield Analysis; CD+Tests done when it reaches QA.

## 5. Proposed PRD Acceptance Criteria

- proposed_prd_acceptance_criteria: (1) A structured run at Brownfield Analysis, CD+Tests or CR shows `✓TP ●CD+Tests ○QA`, from QA on `✓CD+Tests`; the full structured bar is at most 40 columns and the condensed form applies below the full width. (2) The same run, neither waiting nor blocked, shows the label baut / building, the reason "In Arbeit: {gate title}", the build figure inside the accessory region, no animation element in the still pose and the terminal face `(o_o) ⚒`; during an active turn it stays baut. (3) Verified-change, quick-task, block and undecided runs show exactly the status card's path and marks for their mode; no completed quick-task run shows PRD, SD or TP. (4) A transition of the shown run into waiting or blocked raises exactly one toast naming run, state and gate; baseline reads, run switching, repeated equal reads, turns and stale reads raise none. (5) Toasts are on and sound off by default; "Meldung aus/an" and "Ton an/aus" switch them, the sound plays only with a toast, and both choices persist. (6) While switched on, the status line shows `AGDF · {gate} · {short state}` (for example `AGDF · QA · wartet`, `AGDF · CR · baut`, `AGDF · fertig`) or a neutral entry, also with the pane closed and in the terminal; turns do not change it; switching off clears it. (7) Toast and status line offer no action and the companion writes nothing to `.agdf/control`. (8) Every locale shows "AGDF Companion"; the command stays `/agdf-companion`. (9) A template placeholder objective is not shown. (10) Without `.agdf/control`, the companion speaks the language of Claude's `language` setting when it names a supported locale (a language tag such as `de`, or a language name such as `German` or `Deutsch`), otherwise English.
- assumptions: The status line uses gate codes (QA, CR, CD+Tests) for brevity while the panel reason uses gate titles. The build variant covers only the structured build phases named in the UR; compact paths (Compact Delivery, Verified Change) keep the existing läuft figure while their execution mark is current. Toasts use the host's default display time.
