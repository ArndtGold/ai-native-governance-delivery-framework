### Host-aware presentation and remote decision

Select the presentation from confirmed actual display on the current user surface and supported MCP UI, keeping rendering support, qualified decision actions and Core gate readiness separate. A shipped resource, visible rendering or server advertisement alone does not prove a usable native decision path.

| Actual support state | Required presentation | Available decision path |

The compact Chat summary includes undertaking and gate, exact applicable version/presentation reference, goal/scope, material changes or unavailable comparison, relevant acceptance context, open points/risks, an accessible exact-version document, consequence and next actor, and the exact current gate Approval formula with a short explanation of the equal visible approval button where usable; ordinary discussion remains in Chat. The complete Chat fallback contains the full decision context, applicable acceptance summary, exact-version access and that same exact Approval formula, without unavailable-button instructions. SD must select a supported exact-material access mechanism without unauthorized sharing or inventing a second document authority.

The native card and either Chat form are projections of one prepared Core-owned gate/version/presentation, not separate approval requests or independent versions. The concise companion avoids duplicating the entire native card in Chat while retaining the information needed for the remote decision. A deliberate valid response through either route records at most one effective gate approval. The confirmed result resolves the shared decision; other live projections show the current recorded outcome or conflict/expiry, and old immutable Chat messages remain identifiable historical material, never renewed authority. Concurrent click/text, retries, lost acknowledgement and changed material use the existing operation/receipt/current-state rules. Discussion alone never decides. Native qualification and QA evidence remain required independently of a working remote fallback.

The earlier observed card rendered and read the document, but its three decision buttons and comment field were disabled with an explicit package/host qualification warning. Its historical generic ready wording invited a choice. The product must instead state both facts consistently: material may be ready for the supported Chat decision while native actions are unavailable; show the usable route and reason beside the limitation. This observation is not a diagnosis of the underlying qualification failure or native click acceptance.

### Connection lifecycle product rules

The first product limit is **three counted server generations per explicitly owned connection**, including current, starting, draining, closing and close-unconfirmed generations. A candidate reserves a slot before starting. One candidate may be qualifying at a time. There is no uncounted overflow during replacement or cleanup. If full, retire only an already non-current, own and safely idle generation with confirmed end before reserving a candidate slot; never shut down the current usable generation merely to make space before replacement qualifies. If no such slot exists, refuse the switch visibly and preserve existing work. This is a proposed product decision for this PRD approval, not an already approved runtime setting.

A generation becomes current for new views only after startup, exact runtime/resource identity and genuinely declared required host capability are qualified. Failed qualification retains the prior usable path; failed candidate cleanup continues to count. If the prior path has independently failed, explain the real outage rather than claiming it is usable. Concurrent requests yield one current switch, never competing current owners.

Active views/documents, reads, running commands and unresolved command effects stay pinned to their original owner and operation identity. No replacement-induced grace deadline forcibly evicts them. Their existing qualified view-expiry rules continue; expiry/closure cannot be used to replay or migrate a pending/uncertain decision or free a still-owned running command. Retire the oldest eligible non-current own generation only when all these claims are clear, through its orderly close path. Count it until worker/transport/process termination is confirmed. A close deadline may stop waiting and show close-unconfirmed; it never authorizes a forced kill or false freed slot. SD specifies finite technical qualification/close deadlines and verifies their compatible failure semantics before TP; this PRD fixes the user-visible protection/refusal contract.

Reading, refreshing and ordinary navigation do not start replacement. A controlled replacement request targets the already-owned connection and a concrete candidate; it is not blanket reconnection after every timeout. Cleanup of eligible old children is part of that operation. Host connection replacement, external host UI support and user business approvals are not implicit effects.

### Ownership and supported/dependency-blocked outcomes

The existing AGDF launch boundary can control only children it directly creates and confirms. The existing server/executor owns its active traffic; Core owns canonical decision state/receipts; view/session owners retain exact bindings. Codex owns the host connection, real client capability declaration, renderer and native teardown. Shared package-directory ownership does not prove ownership of running processes in other connections. The generation owner must preserve executable/resource bytes still needed by any retained connection.

SD must establish a feasible supported control surface at this bounded launch boundary, with request/resource routing and generation identity. If it cannot do so, it must report that dependency and block the affected design rather than invent a global process controller. Missing Codex capability/teardown support is likewise explicit. Headless inspection/text remains usable where already supported, but cannot satisfy native card acceptance. The original UI-capability loss must be located and qualified independently; a pool alone cannot be reported as its fix.

Current historical completed references evaluate blocked under newer closeout checks. Preserve their stored historical completion/approvals/bytes; show historical completion and any unavailable current validation separately. Do not portray historical insufficiency as a new authorized closeout task, silently fabricate bindings or claim it meets today's evidence requirements. Valid newly completed flows retain the normal completed state. SD must qualify a compatible read/diagnostic transition, not rewrite protected references.

## 4. Activation, Blockers, Recovery And Transitions

Existing Request Activation binds an explicit delivery intent to its target/Run. Pure status remains read-only. Opening a document or changing a view does not approve or invoke a write. Each operation revalidates its exact expected state and applicable gate/source/presentation binding. The actor can obtain concrete supported-input guidance before invoking it.

Missing prerequisites name the responsible actor and applicable next step. Stale/foreign bindings, invalid seal or incompatible runtime block the dependent operation. Malformed inputs name source/field/form and supported correction. Unsupported revision/lifecycle states do not turn into raw edits. Busy/read/check unavailability remains unavailable; a supported repeat action is visible. A lost write acknowledgement shows effect uncertainty and retains original operation identity where replay is supported. Conflict/concurrent change/pending transaction requires the existing bounded recovery, not blind repetition or a new invented decision.

Transitions preserve distinct meanings: draft -> registered -> exact presented material -> new deliberate response -> confirmed decision effect -> current evaluated next operation; analysis/review registration -> satisfied internal input, not human approval; revision preview -> allowed apply -> changed dependencies and renewed obligations; failed/uncertain response -> inspect/retry/recover -> fresh current state; QA pass before approval -> human decision pending; revise/block -> owned obligation; accepted applicable QA/UAT plus valid OR/requirements -> governance completion. Completed -> history inspection does not reopen closeout.

View or interaction closure ends that interaction without approval/completion. Actual backend teardown is evidenced separately. Old asynchronous read/check results must not revive superseded state after refresh, revision or expiry. The general cockpit remains a reader of Core descriptions and retains existing draft checks. Only the focused bound decision card adds contextual approval or already-permitted continuation; Core change/reject remain supported and historical results inspectable, without primary card controls. Normal discussion/edits record no formal decision automatically; it cannot submit arbitrary Run updates. A user click is the gate decision. A host execution-permission prompt is not another gate decision and cannot by itself approve material.

Replacement transitions are candidate-slot reservation -> qualifying -> verified new current -> prior generation retained/draining -> safely idle -> orderly closing -> confirmed freed slot. Failure before admission retains the previous usable current; capacity/close uncertainty yields explicit refusal/recheck, not forced eviction. Original business-operation UUID/receipt/recovery survives these transitions; a delayed success cannot revive an expired/superseded view. Transient runtime retry is visible and never a disguised approval resubmission. New generation qualification preserves actual host declarations rather than inventing them.

Changing display mode or moving between Mac and iPad does not prepare a second independent decision. Both views revalidate the same exact material/current eligibility; completion through one route makes the other no longer eligible to decide again. A qualification warning cannot coexist with an unqualified instruction to choose disabled native actions. Keep document/read readiness, native action support and the supported Chat decision route visibly distinct. Missing remote access blocks remote decision readiness; support loss selects the honest Chat fallback without waiving native acceptance.
