## 1. Problem

The user asked the agent to record places where delivery requires code searches or direct Core calls as MCP candidates. Two cockpit runs exposed repeated searches for authoring formats and writer arguments, inconsistent next steps after approvals, manual structured closeout work and ambiguous current versus historical evidence. The user explicitly wants a coherent architecture and flow rather than isolated fixes that accumulate conflicting responsibilities.

The requested architecture assessment was created outside AGDF in `docs/reviews/ARCHITEKTUR_FLOW_MCP_KANDIDATEN_20261010.md`. It groups all recorded candidates into thirteen groups and compares them with existing architecture and source owners. It identifies four related weaknesses: incomplete state preparation in writers compared with readers; description text used as an execution condition; incomplete structured closeout and completed-state projection; and authoring/evidence contracts that require avoidable source inspection. Existing typed approval commands and document-state projections provide reusable owners, but their existence alone does not complete the lifecycle through MCP.

These findings are source analysis and historical execution observations. The assessment did not reproduce the failures through new runtime tests. Some candidates are already implemented or are ordinary engineering inspection rather than missing product APIs. Treating every candidate as a new MCP tool would create competing policy and duplicate functionality.

The requested integration of the decision card originally exposed a further concrete gap: at SD, the approved UR could not be reopened through the then-supported revision boundary. The bounded Core bootstrap recorded below has since implemented that capability. This historical finding remains an acceptance scenario, not a claim that the current capability is absent. Users need a controlled way to change the earliest approved source within the same Run, preserving history and obtaining renewed decisions instead of creating a replacement Run solely to work around the gap.

A later, independently verified routing defect returned an ordinary status/approval card when a draft-authoring revision action was inapplicable to an already approved source. This combined a caller route error with a Core diagnostic defect: an approved-source change needs the existing source-revision preview/application contract; an unapproved draft uses the authoring route. The scoped dispatcher repair distinguishes those cases and has repository/generated-package evidence, but no newly qualified installed/native evidence. The UI discussion also clarified that three primary decisions add unnecessary ceremony: Core retains its existing approve, request-change and reject capabilities, while the normal user journey uses a contextual approval or permitted continuation and handles discussion in Chat.

The native qualification also exposed a connection whose required UI capability is unavailable, repeated host restarts and ambiguity about multiple server processes. The user requests a bounded replacement arrangement that retires the oldest eligible unused server. Multiple processes may belong to different chats; age alone establishes neither ownership nor abandonment. The existing diagnostic evidence does not prove that old servers cause the missing capability. This renewed source separates that unresolved native diagnosis from the requested lifecycle improvement.

New requirements may arise throughout an active Run before deliberate UAT approval, including during implementation, QA and UAT preparation. Reopening UR for every change would discard unaffected decisions; inserting a changed need only into TP would leave implementation inconsistent with approved intent. The same flow must identify and explain the earliest source whose binding statements change, then assess its actual dependencies. A defect against unchanged approved requirements/design is an implementation correction, not automatically a requirement revision.

## 2. Goal

Provide one bounded, coherent delivery flow from recording artefacts and evidence through presentation, deliberate human approval, permitted revision and governance closeout. Core, CLI, MCP and the relevant cockpit views must describe the same bound current state and the same permitted next operation. Routine use of supported operations must not require manual control-table edits or source searches to discover input formats.

MCP makes qualified existing Core capabilities available through explicit contracts. The app consumes the resulting current state, document identity, evidence and next-step descriptions. Human decisions remain deliberate and bound; governance completion remains separate from Git or publication actions. The UI offers one contextual primary action: approval at an eligible human gate, or the next step when Core already permits continuation. Core request-change and rejection capabilities remain available under their existing contracts without becoming primary UI buttons. Users inspect the exact document and discuss changes in Chat. When the approval UI is actually displayed on the user's surface, Chat introduces that card briefly and gives the exact current Approval formula as an equal alternative. Otherwise Chat provides the complete decision card and exact material access, including on iPad. Both approval routes converge on the same eligible presentation/version and one approval effect; later discussion may still be followed by the exact formula while that presentation remains current.

Extend the canonical revision capability for active structured Runs before deliberate UAT approval, choosing the earliest affected UR, PRD, SD or TP rather than always returning to UR or using the current gate as the classification. Preserve the already qualified approved-UR-at-SD scenario within this broader requirement. Core owns binding, lifecycle eligibility, dependency impact, history and state transition; CLI and MCP expose the same operation and the app displays its result. Semantic classification must be explained against concrete source statements, not inferred solely from the current gate or file names.

Permit controlled replacement of explicitly owned server generations without losing active views, replaying decisions or affecting another chat. Establish the connection lifecycle owner before designing this behavior; native capability and closure claims require actual host evidence. Retain existing code and tests as historical work requiring renewed plan fulfillment, rather than treating the reopened sources as a completed implementation.

## Affected Users

- Users directing delivery who need a understandable current state, current decision evidence and a reliable next step.
- Coding agents consuming AGDF contracts, including models that benefit from less schema discovery and fewer contradictory results.
- Reviewers and operators verifying revisions, artefact identity, recovery, approvals and completed-run/backlog consistency.

Improved performance of weaker models is an expected benefit to evaluate, not an already measured fact or a guarantee for every model and host.

## 4. Non-Goals

- One new tool for each candidate, a universal code-understanding service, a general orchestration store or a second policy/approval authority. Only the bounded connection lifecycle in scope 9 is added; its owner must avoid a parallel governance source of truth.
- Automatic gate approvals, inferred human decisions, removed gates, weakened source seals or unbound target/run/revision operations.
- Stronger independent host enforcement or independent human-response proof merely because an operation is reachable through MCP. Existing cooperative assurance must be described honestly.
- General owner/test inventory, synthetic product-facing test sessions, installer migration, blanket automatic reconnection/restart and qualification of all hosts/models. Only explicitly owned, bounded generation replacement in scope 9 is included. No automatic decision replay, global PID ring, foreign-chat eviction or modification of installed Codex binaries. Narrow diagnostics and fixtures necessary for this flow remain separated from productive operations; native qualification cannot be replaced by remote iPad confirmation or synthetic tests.
- A general cockpit redesign, arbitrary app writer access or reimplementation of the completed document-state and draft-check slices. Only the explicit bound gate-decision interaction is added.
- Removing Core request-change or reject capabilities, migrating historical decisions, or treating ordinary Chat discussion as an automatically recorded formal decision. The simplification concerns the primary UI actions and coordinated Chat presentation.
- Changing Request Activation, treating read-only questions as delivery authority, silently editing approved or foreign runs, or transferring their approvals.
- Automatic UR restart or blanket revocation of every gate for any new requirement; misclassifying a changed requirement as a TP-only correction; reopening completed UAT or a closed Run through this pre-UAT extension.
- Commit, push, release, deployment or publication; completing unrelated active runs.
