## 3. Test Plan

### Focused implementation checks

Extend existing owners instead of creating parallel control logic. T-000 confirms exact files and available script names before implementation; an equivalent existing owner may host a scenario with its actual location recorded in FOCUSED_CHECKS.json. New tests prove observable state/contract failures, not implementation-shaped assertions.

- Core/shared dispatch tests and packages/cli/scripts/skill-dispatch-test.js, skill-dispatch-function-contract-test.js, intake-continuation-test.js plus existing binding/run-assignment tests: continuation order, direct assignment, ready-draft presentation, decisions-open clarification, prerequisite and forbidden-stage matrices, shared revise input and stale assignment.
- Focused prd-definition-test.js, existing control-command/process tests, run-revision, run-step-transaction/recovery/lock, prd-readiness and presentation/localization tests: run the actual built writer/presentation path with exact source proofs, valid and negative replacement, approved-destination protection and supported interruption/replay. Avoid hand-authored receipts. Observe both the dispatcher denial and the writer's own independent mutation guard.
- Existing packages/mcp-server/test contract, continuation and protocol suites: exercise valid/invalid prd_action through the built candidate, same canonical contract and generated schema. Do not accidentally test registry create-agdf from before this change; existing package-consumer fixtures must resolve the current locally built Core/CLI.
- Existing skill conformance, name projection, runtime-reference/integrity, request-activation, instruction-footprint, Copilot profile/installer and payload tests: canonical ownership, four generated profiles, exact measured growth and unchanged exclusions/limits.

Test-owned temporary runs may use existing synthetic approval fixtures. Label them test authorization, not deliberate approval of a production run. Recording/recovery fault injection uses the existing transaction harness while executing the real operation. Preserve failed attempts and later successful evidence rather than erasing their provenance.

### Actual semantic observations

T-005 reads the implemented skill/contract, obtains actual current built CLI/MCP authoring bindings for isolated test-owned runs and performs the four stated semantic cases. Retain the complete input/output and observed question/draft/card, not a prewritten expected fixture passed off as model execution. After each permitted draft, use the actual typed registration and fresh control evaluation. For complete inputs, observe the lack of a redundant product question. For material gaps, observe a preserved draft, the actual bundled question and presentation denial, then the supplied answer and fresh readiness. For revision, evidence human editing intent separately from skill selection and retain both presentations. For conflicting intent, protect the approved UR and record the existing permitted revision next step.

Each observation names author/reviewer, source/candidate/contract identity, actual canonical target/run/revision, protected-source digests, assumptions/known unknowns, result and reasoned semantic evaluation. Persist complete-request, incomplete/answered, revision and conflict outputs in PRD_BEHAVIOR_CASES.json; PRD_BEHAVIOR_REVIEW.md assesses meaning against the approved inputs. Cooperative root-agent observation is the allowed evidence lane. Missing actual observation remains evidence_gap; passing deterministic fixtures cannot replace it. A fresh installed native-host campaign is outside this plan and is not a success claim.

### Final candidate qualification

After focused checks pass, qualify the final candidate through the existing processes, sequentially when they share generated/package directories:

1. npm run build; verify canonical source-to-generated/package parity, then prepare existing local package-consumer fixtures as their documented process requires. Package setup must use this candidate, not older registry code.
2. npm --prefix packages/cli run smoke-test, including the new meaningful PRD cases and unchanged existing guards. Run npm --prefix packages/mcp-server test separately only if the same candidate's full MCP suite was not already covered or later changes require it. Existing performance thresholds and cold/warm sample policy remain unchanged.
3. npm run test:maintenance-contracts, npm run test:host-compatibility and npm run compatibility:check. For legitimate changed source fingerprints use existing compatibility:record first, retaining historical native evidence as historical. Run required community-health/package-boundary checks for affected docs/packaging surfaces.
4. Measure exact existing payload/instruction inventory before and after; an exact observed baseline adjustment may be necessary, but no limit increase, fabricated evaluation or blanket growth allowance. Verify built aliases/function schema, runtime-module references, four profiles and existing evaluation expectations.
5. Reconcile existing context ownership; perform final Code Review, Clean Implementation Review and Task Plan Review against the same final candidate. Resolve findings through the existing owner and rerun only affected checks unless a broader unresolved concern warrants more.

Logs retain command, exit status, source/candidate digest and relevant scenario IDs. Final summaries report only completed checks. After code fixes, refresh affected evidence and source identity; do not keep a stale green summary. No implementation test is claimed by preparation of this TP.

## 6. Risks And Blockers

- Competing semantic ownership, generic fallback enabling a writer, missed source/UX/seal blocker or unauthorized approved/foreign-state change: block and route to the existing control/source owner.
- New material product/design requirement beyond approved UR/PRD/SD: return to the earliest affected artifact; do not silently expand the plan or resolve product intent in code.
- Missing task/scenario mapping, actual semantic observation, final candidate identity, source proof, review or exact budget evidence: revise/evidence_gap until satisfied. Synthetic authorization and cooperative review never become human or independent evidence.
- Stale draft/presentation, invalid localized completeness or failed recording: use existing revision/recovery and fresh presentation; never weaken the guard, reuse an old reply or hand-write receipts.
- Legitimate generated/inventory drift: prove the exact source cause and observed delta using existing owners. Unexplained growth or weakened tests/limits remain blockers.
- Context reconciliation open_gap or unresolved final finding: prevent clean closeout; normalize findings to UR, PRD, SD, TP, CD+Tests or evidence_obligation. qa-gate alone decides pass/revise/block.
