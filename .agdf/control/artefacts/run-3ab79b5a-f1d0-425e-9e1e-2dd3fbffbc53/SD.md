## 1. Solution Overview

Extend the existing Core resource/configuration boundary with one validated preference resolver. Package its defaults as plugin-owned JSON, derive a shortened public MCP input schema from the existing complete Core contracts, and resolve omissions before invoking the existing operation owner. Ship these changes together. Neither JSON distribution alone nor optional discovery fields without executable defaulting fulfils the approved PRD.

This design derives from the approved PRD (sha256:81229effc36ffb32a5606bb7b666ecada7de9f747e4901bba7082f1f79d51dc8), approved UR (sha256:71744bb809ba40aac3247959949632f67ad21d5a8808f84cb523a40455afee1b) and completed Brownfield Review (sha256:beb66e3bbb7d9fc61280d0d0ff0b740758a4d8aa4a1d72677c62e4180d768ccb) of this Run. Product choices are fixed by that PRD; this document specifies their technical realization, not additional acceptance requirements.

A new call validates the caller's supplied fields, obtains a valid execution directory, resolves only the already supplied target provenance, reads that confirmed project's configuration once, resolves eligible preferences, and validates the complete internal input. It then invokes one existing operation owner. Targetless calls use plugin preferences only. Retried commands instead recover their original resolution through the existing operation family before considering today's preferences. Prepared documents remain immutable.

No new dependency, MCP tool, approval owner, configuration hierarchy or recovery ledger is selected. Current source inspection is design evidence; this Run has not implemented or tested the feature.

## 3. Architecture Decisions

- SDD-001: Store the four preferences in the adjacent versioned defaults JSON and schema named above and load them through createResourceContext; rationale: existing generatedURL/package version binding already owns resources, while a hardcoded runtime map or second project file would duplicate values; consequence: resource manifests, projection and package closure must carry both files and fail when absent or incompatible.
- SDD-002: Resolve validated explicit call values over the confirmed project's recognized values over plugin values in one Core helper; rationale: resources/context.js currently has separate silent catches while control-configuration.js classifies activation independently, so defaulting must not erase invalid-control or setting errors; consequence: affected consumers converge on explicit diagnostics, preserve existing initialization locale selection, and never write configuration while reading it.
- SDD-003: Derive public MCP schemas from complete canonical contracts and normalize once at the existing adapter boundary before complete validation; rationale: server.js performs SDK validation before execution and current MCP runtime parsers require full fields; consequence: discovery, SDK validation, parent-owned operations and Worker dispatch all accept the same omissions immediately, while old valid explicit calls and strict authority checks remain.
- SDD-004: Keep working_directory explicit on the currently evidenced native adapters unless an adapter supplies a validated task-execution context through private runtime wiring; rationale: launcher fork paths inherit process cwd but current trustedContext contains surface/version/provenance, no task-directory binding, and neither client metadata nor inherited cwd alone proves the intended task context; consequence: omission is publicly accepted but returns working_directory_required before effect on those adapters. No host is claimed to support cwd omission merely from its name. No fallback to target, installation directory, environment preference or inferred repository is permitted.
- SDD-005: Apply route only to presentation.deliver and variant only to agdf_inspect gate-check, using existing presentation/status owners; rationale: these selectors already choose representation rather than authority; consequence: no implicit prepare/approval, no variant injected into another operation and no UI capability bypass. A prepared document's selected language and bytes remain original even if a new delivery uses another route preference.
- SDD-006: Retain resolution data inside each existing operation family's pending/receipt or connection-local state, atomically with its original request identity; rationale: runCommandRequestDigest currently hashes the entire complete envelope, and current receipts retain a digest rather than enough data to reconstruct omitted fields after config changes; consequence: additive versioned reader/writer changes are required at existing owners. Simply recalculating defaults or dropping resolved fields from the existing digest is rejected.
- SDD-007: Expose bounded effective values/source through existing inspection/help and use the existing tool-error projection for new input/configuration failures; rationale: an extra configuration call before every operation defeats input relief, and metadata alone may not be visible to the model; consequence: ordinary calls resolve internally, existing help/report content shows provenance on demand, and no new lookup step or error authority is introduced.
- SDD-008: Regenerate and verify one candidate carrying both configuration and executable MCP relief within unchanged hard budgets; rationale: the Brownfield Review identifies public-contract depth and little descriptor headroom, while the PRD excludes a JSON-only intermediate delivery; consequence: focused regression, both SDK eras and fresh candidate-bound Codex CLI evidence precede QA claims. No new external technology or major version is selected; evidence is the in-repository dependencies and current owners inspected on 2026-10-30.

## 4. Integration Points

### Resource and configuration resolution

The defaults document is small, data-only and fully validated at resource-context creation. Do not implement fallback literals for a missing/corrupt installed resource. Existing resource-provenance failure handling reports repair of the matching runtime. The JSON schema and runtime validation share existing enums/language validation rather than creating different accepted sets; no schema-fetch network dependency is allowed.

Read a confirmed project's config once per new call using the existing contained control/resource reading boundary. Do not key a mutable global preference cache by cwd or by whichever project was used last. An immutable per-call snapshot contains the recognized normalized preferences, source identities and config digest. A targetless request does not inspect cwd for project settings. Target resolution uses only existing explicit target_source/primary_target and existing eligibility checks; defaults cannot select them.

Check the document/control classification first, then all present recognized preference fields. A present malformed recognized value is an error even if an explicit value would otherwise take precedence; an override is not a config repair. Distinguish absent optional keys, null allowed for gate_check_variant, and invalid null/type/value for the other settings. Preserve the existing activation checks and runtime_language semantics; runtime_language is not a new configurable preference. Recognized language values use the current canonical tag rules. Valid unsupported presentation tags select the existing complete English pack; malformed tags and a broken locale registry fail visibly. Artefact-language canonicalization continues through the existing artefact owner and cannot be changed by presentation_language.

Existing explicit setup-language choices and system-locale selection during deliberate initialization remain. They produce stored project choices, which outrank plugin defaults thereafter. Where no valid locale choice is available the existing English fallback is read from its owner. Configuration generation/update code must preserve existing project bytes on plugin updates; any already-authorized explicit language change must retain optional preference siblings and unrelated extension values rather than reconstructing the old five-field-only object. Normal MCP calls perform no configuration write or automatic migration.

### Public input to complete Core input

| Surface | Eligible public omission | Completion and restriction |
|---|---|---|
| Nine regular core MCP tools | presentation_language | Explicit valid tag, otherwise confirmed-project chat_language, otherwise plugin value. Preserve explicit request-language guidance. |
| Seven command groups | schema_version; assurance | Supply the exact current constants from command/assurance owners only. Wrong explicit constants are rejected, never overwritten. |
| agdf_prepare presentation.deliver | command.payload.route | Use explicit route, otherwise resolved presentation_route. Other commands get no route. |
| agdf_inspect gate-check | variant, already optional | Explicit variant wins; null preference means leave existing ordinary report behavior. No variant is inserted for other operations. |
| Eligible regular tools; Cockpit open if wired | working_directory | Explicit absolute directory, otherwise private trustworthy task-execution context, otherwise working_directory_required with an explicit-directory corrective action. Current native adapters have no proven context source and take the last path. |

Projection removes required entries only where allowed by these operation conditions. It retains properties, bounds, enums, consts, additionalProperties restrictions and every conditional authority requirement. A missing working_directory is schema-valid so the adapter can return the actionable context error; malformed explicit input is still schema-invalid. Unknown fields, wrong constants and invalid explicit values fail before resolution/effect. Public and complete validators both count their inputs against existing limits; completion cannot overflow an internal envelope unnoticed.

The normalization entry first structurally validates the public input; obtains explicit/trusted cwd; validates target binding through the existing resolver; consults an existing original operation if applicable; otherwise resolves a per-call config snapshot; supplies eligible values/constants; and runs the unchanged full semantic parser/command validator. It passes a complete envelope plus private resolver context to the existing executor. No language-based second gate evaluation or speculative write is used to discover settings. Error projection/rendering receives the effective language even when the original public request omitted it.

Both parent-owned material/delivery/doctor paths and Worker paths must use that same entry. Resolve once, carry an immutable bounded private snapshot through the existing generation/Worker transport and never send caller-invented trusted fields. Core rechecks full input and current authority/revision under its existing locks. For a new mutating operation, verify that the selected config snapshot still matches before committing the first effect; changed settings require an explicit retry with no effect, rather than mixing snapshots. Once an operation is pending/recorded, use its original snapshot, not the current config.

The private directory context, if a future adapter supplies it, must be bound to the active invocation/connection, name its adapter source and be an absolute validated execution directory. It must travel only through server-owned wiring. Tests may inject this through private seams to establish success and isolation; that is not native-host qualification. This Run does not add a public cwd-trust flag, environment override or host context protocol.

### Original operation and immutable material

Use a bounded input_resolution object within the existing family-owned record, never in the caller's complete command schema. It contains a format version, a logical-request digest, the small allowlisted resolved fields and their provenance, and the effective complete-request digest. A logical request is the validated public input with explicit/omitted presence retained, using the existing canonical material-identity normalization; it contains no default-derived values. The effective digest remains the existing runCommandRequestDigest of the complete envelope, with no change to its algorithm. No full material bytes, arbitrary config object, secret, approval text or second receipt is copied into resolution metadata.

The original operation lookup is target/Run/kind/UUID-bound using the existing status owners; run.create uses its existing deterministic Run identity. For a known operation, compare the original logical digest first and reconstruct only omitted eligible fields from its retained resolution. Revalidate the reconstructed full input and its original effective digest, then let that same family return/recover its historical result. Different explicit values, payload, bindings, or omission shape on that UUID are a different logical request and are rejected as operation_payload_conflict. A new UUID resolves current settings. Constant wrongness remains invalid even on replay.

| Existing family | Resolution retention and replay boundary |
|---|---|
| Run creation, step/artefact/approval/closeout and source revision | Add bounded resolution to the existing transaction context, prospective outputs/pending record and authoritative family receipt. Existing locks, seals, source bindings, archive verification and recovery validate it atomically. No adjacent sidecar ledger. |
| presentation.prepare | Extend the existing immutable presentation envelope/version and its operation lookup with resolution binding. Retain document language, material, digest, revision and identity. Delivery/read never rerender it from current config. |
| project.initialize | Extend the existing initialization operation/owned stage/receipt versions. Resolve original setup context before new settings; preserve existing plan/language preference and original UUID status/recovery. No Run is fabricated for setup. |
| closure.preview/apply | Extend the existing closure preview record and its existing apply/per-Run receipt path with the public operation binding/resolution. Preserve preview identity, exact confirmations and existing closure eligibility; do not add a global operation ledger. |
| material.stage and presentation.deliver | Retain resolution in the existing bounded generation-local transfer/delivery state for the original operation. Expiry/loss remains material_state_unavailable or delivery_state_unavailable, not permission to infer absence or repeat a question. Original prepared document stays authoritative. |
| runtime_generation.replace and recovery/preview commands | Carry resolution with existing generation-controller or original pending-operation binding. Original uncertainty, lifecycle checks and confirmations stay authoritative. Lost original context requires existing observation/recovery, never a new effect with freshly selected preferences. |

Readers accept legacy supported record versions unchanged and validate the new version's bounded resolution at the existing owner. Emit a new family version only for records carrying the extension; legacy full explicit requests retain their existing replay path. Do not modify historical files to backfill metadata. A legacy operation cannot have used this newly introduced omission form; if a retry with omissions cannot be proven against an old receipt, require the original explicit request instead of guessing. Old binaries need not consume a newly written record version: they must reject it clearly through existing version/integrity checks; downgrade rewriting is excluded. This is a forward-reader compatibility change, not a project-config migration.

For pending or unavailable/ambiguous original status, preserve existing effect_unknown/recovery_required and original UUID instructions. Never treat a missing local cache, unreadable record or changed config as proof that a write did not happen. Returning an original historical effect and observing current state are separate; a newly invalid config may be reported as a current-observation limitation without altering or reexecuting the historical effect. Existing identity reuse protection remains global to the applicable family/Run, not merely a convenience in the adapter.

### Provenance, diagnostics and guidance

Extend existing agdf_inspect contract/help report content with effective_configuration: four bounded setting rows with normalized value, source (explicit, project or plugin), declared default, applicable source identity/digest, and whether the value is current or original-operation/presentation-bound. Existing operation-contract help also identifies constant-owned inputs and eligible public omissions. No new MCP tool or mandatory preflight call is required; a normal shortened call resolves internally. Optional transport metadata can carry the same bounded projection, but model-visible inspect/help content is the required observation surface.

Use the existing mcp-tool-errors.js input/error projection and localized message registry. Add typed correct-input causes configuration_invalid and working_directory_required and a bounded setting-source diagnostic (source kind/path, allowlisted field, recovery action; no raw config contents). Extend the same registry/diagnostic allowlist rather than converting arbitrary exceptions to trusted causes. Configuration source changes before a new effect use the existing stale-snapshot/retry pattern. Malformed defaults/resources use existing runtime repair handling. Preserve ordinary missing/invalid control reports and their setup boundary. No error triggers automatic setup, permission escalation, re-execution or config repair.

Update canonical plugin interaction/task-target/skill guidance and shared MCP docs together: language matching the resolved preference may be omitted, while a different deliberate request language must be sent explicitly. Request activation, target provenance and all existing gate/revision/digest/reply obligations remain. Reassess the existing CG-MCP-DISPATCH-ADAPTER context-graph node to link the finalized resource/resolver owner and replay boundary; no competing configuration authority node is required.

## 5. Constraints And Compatibility

Existing valid explicit clients keep their accepted values and operation semantics. The only intended expansion is the PRD's eligible omissions; this is not the prior schema-only acceptance-parity repair. Invalid explicit inputs and unknown fields remain errors. Presentation preference cannot select a Run, replace an artefact, infer a revision or satisfy an approval. Target_source, primary_target, target_id, run_id, expected_revision_id, operation_id, presentation/material identities, digests and deliberate replies remain explicit wherever the current operation requires them.

The existing complete project file remains valid without either new preference. Adding defaults does not make an incomplete legacy file active. Normalizing a syntactically valid tag is not translating or rewriting approved source bytes. Existing presentation documents retain their original bytes even after plugin or project preferences change.

Project preferences are per confirmed target and per call; runtime resources are immutable per matched generation. No selected-project state is shared between concurrent requests. Any new private metadata is measured within existing request/result/transport/material/state limits; no limits are raised. Descriptor headroom is particularly narrow (the inspected source had 4,998/5,000 bytes for inspect and 24,552/24,576 for command-plus-decision definitions). Optional projections and concise guidance must fit; do not duplicate the full settings schema in every tool description. Generated payload baselines may be regenerated with the actual justified files, but hard caps and closure rules remain.

CONTRIBUTING.md and GOVERNANCE.md remain applicable. Preserve unrelated staged/unstaged installer and control work. This design grants no Git action, global installation, release/publication, automatic-check permission, native UI acceptance or broader host support.

## 8. Risks And Open Questions

The largest implementation risk is record compatibility: current full-envelope digests cannot recover missing preference values by themselves. The chosen resolution is existing-owner record extensions plus unchanged effective digest, with legacy readers and atomic recovery tests. This must be delivered with defaulting; an adapter-only cache is not an acceptable partial implementation. Exact family field validators/next record version numbers are mechanical implementation details within that decided boundary, not permission for a new ledger or a different replay identity.

Native execution-directory provenance is deliberately unresolved by the existing host evidence, but the architectural behavior is resolved: explicit directory required on the current adapters and actionable rejection on omission. A later supported trusted source requires its own evidence; this Run does not promise a native cwd shortcut. This preserves the PRD's conditional requirement while still delivering the other immediate MCP omissions.

Recognized-invalid handling changes previously silent low-level fallback and must be confined to applicable preference consumers. Resource loading, tight payload budgets, broad generated surfaces and concurrent config changes require the stated focused proof. Discovery success alone proves no executed operation, UI acceptance or task-efficiency improvement. No remaining product or architecture choice is deferred to TP; actual evidence and exact task allocation remain future work.

Dieselbe UUID übernimmt nach Konfigurationsänderungen keine neuen Werte; abweichende logische Anfragen werden abgewiesen. Dafür werden bestehende Belegformate versioniert erweitert, ohne separates Journal oder Umschreiben alter Belege. Der neue Reader unterstützt alte Formate; alte Binärversionen müssen neue Formate gegebenenfalls ablehnen. Vorbereitete Entscheidungen behalten Sprache, Material und Identität.
- Darstellung und Diagnose: Route gilt nur für presentation.deliver, Statusvariante nur für lesendes gate-check. UI-Fähigkeiten und Freigaberegeln bleiben bei ihren bisherigen Ownern. Bestehende Hilfe und Inspektion zeigen wirksame Werte samt Herkunft. Ungültige Einstellungen nennen Quelle, Feld und Korrekturschritt; kein Aufruf repariert oder aktiviert die Projektsteuerung automatisch.
- Nachweise und Risiken: Alle zwölf PRD-Kriterien sind dem Design zugeordnet. Tests müssen insbesondere alte explizite und neue verkürzte Aufrufe, ungültige Eingaben, Projekttrennung, unterbrochenes Replay und unveränderliche Präsentationen prüfen. Generatoren, feste Größenlimits und beide SDK-Protokollvarianten bleiben verbindlich. Hinzu kommt ein isolierter, exakt kandidatengebundener Codex-CLI-Nachweis mit lesendem Aufruf und synthetischer Schreiboperation. Repository-, native CLI- und UI-/menschliche Abnahme werden getrennt ausgewiesen.
- Grenzen: Noch keine Umsetzung oder Feature-Tests, keine Installation, Git-Aktion, Veröffentlichung oder allgemeine Host-Freigabe. Die größten technischen Risiken sind die Erweiterung bestehender Belegformate und knappe Schema-/Paketbudgets; ihre Prüfung ist verbindlich, keine offene Architekturentscheidung.
- Entscheidungen und nächster Schritt: Alle acht materiellen Designentscheidungen sind aufgelöst. Nur konkrete Taskreihenfolge, Fixtures und Prüfkommandos folgen im TP. Approval: SD erlaubt die Task-Plan-Erstellung; Umsetzung folgt erst nach den weiteren erforderlichen Freigaben.
