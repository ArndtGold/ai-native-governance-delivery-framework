## 1. Solution Overview

Replace the Cockpit's default backlog projection with an adapter over the existing stored Run inventory. The overview identifies undertakings and their recorded attention state; opening one exact Run invokes the existing current-detail evaluation. Active Runs and history remain reachable in the desktop and compact MCP surfaces. An optional separate Legacy backlog view preserves information that has no Run. Neither overview reading nor legacy reading writes control state.

Remove the central backlog from new Run mutation plans, ordinary locking, required control files and gate prerequisites. Reuse the existing Run writer, seal, source binding, material journal and operation receipt owners with no backlog output. Keep old transaction decoding and explicit recovery of their captured outputs. There is no replacement index file, inventory cache, global Run registry or background synchronizer.

Define one normative placement rule for newly chosen Git worktrees under the owning primary checkout's `.agdf/worktrees/INITIATIVE/`. Existing assignments and explicit alternative locations remain valid. Placement is a process convention, not an automatic worktree manager or cross-checkout authorization mechanism.

## 3. Architecture Decisions

- SDD-001: Project the default overview from readRunInventory within the existing bounded Cockpit read view; rationale: discovery and pure inventory already own membership, title, attention, lifecycle, activity and deterministic ordering; consequence: overview remains stored orientation and performs no per-Run gate, seal, QA or document evaluation.
- SDD-002: Reuse inventory order and fields for Active, History, counts and selected-area search; rationale: one projection prevents desktop, compact and CLI semantics from drifting and eliminates incidental heading-fetch effects; consequence: Run-ID title fallback and unknown activity remain explicit, and the main list has no UR-heading enrichment dependency.
- SDD-003: Retain exact per-snapshot target, Run, revision and resource binding for detail and freshness; rationale: saved inventory state cannot authorize delivery or silently choose another Run; consequence: source changes invalidate old selectors and require refresh or safe return while visible stale detail never becomes current by inference.
- SDD-004: Retain the old parser behind an explicit separate read-only legacy scope; rationale: planning-only rows and old source links cannot be reconstructed from Run files; consequence: legacy loading and its failures are isolated from default Run discovery and never create, migrate or repair Runs.
- SDD-005: Write new Run operations through the existing transaction owners with backlog null and only the applicable Run/output locks; rationale: current journals already support a null backlog and preserve the existing atomic Run commit point; consequence: ordinary operations cease shared backlog projection, synchronization and locks without inventing a journal format or reducing seal, replay or source checks.
- SDD-006: Preserve old journal versions and complete any recorded legacy backlog output only through explicit supported recovery; rationale: an old transaction's captured old/next bytes and receipts remain obligations even after normal projection ends; consequence: legacy pending work blocks conflicting mutation until recovered, while new Run-only transactions recover without a backlog lock and independent new Runs do not block one another for a nonexistent shared output.
- SDD-007: Make the backlog optional across setup, diagnosis and control dependencies; rationale: removing only the UI or writer would leave hidden operational requirements; consequence: fresh setup omits a live backlog, existing bytes remain, legacy-only findings stay scoped to that view and current Run/source relationships replace control uses of backlog pointers.
- SDD-008: Version the changed Cockpit envelope and paired resource as v2 while retaining governance and persisted Run formats; rationale: replacing backlog membership and adding a separate legacy scope is an incompatible Cockpit data meaning and must not be silently interpreted by old UI code; consequence: ship matching Core and generated UI together, reject unsupported envelopes, preserve generation-pinned old sessions and require a coordinated runtime cutover rather than mixed old/new writers.
- SDD-009: Define new worktree placement under the owning primary checkout and require ignore verification before creation; rationale: a stable location reduces scattered working copies without confusing Git isolation with Run authority; consequence: reuse assignments, support grandfathered and explicit alternate paths, prevent recursive placement and collisions, and add no automatic create, move, switch or cleanup operation.
- SDD-010: Perform feature work and verification only in this assigned isolated worktree and reconcile the independent CI result before integration; rationale: runtime, workflow and generated baseline work can be shared outside Git isolation; consequence: no live foreign-worktree mutation, plugin reinstall, workflow/baseline weakening or full-suite execution during design, and every eventual claim remains tied to its tested revision and environment.

## 4. Integration Points

### Read flow and visible states

The unqualified Cockpit snapshot selects the Run overview. Its bounded read capture calls the existing inventory reader once and adapts its result into a `kind: runs` scope, carrying inventory rows, diagnostics, lifecycle/attention counts, source coverage and the existing snapshot identity. An internal adapter may live beside `cockpit-backlog.js`; it contains serialization and view-state mapping only. It must consume the shared inventory result rather than rediscover files, derive another attention algorithm or fabricate approval state.

Capture directory membership of `.agdf/control/runs/`, consumed Run files and configuration through the existing control-read abstraction. Membership changes, changed source bytes and optional dependencies actually consumed participate in freshness. The list does not recursively scan `.agdf/worktrees`, Git history or every artefact directory and does not pre-evaluate detail for all discovered Runs. Use existing file, total-byte, response, time and session limits; do not raise them to make a test pass. Within those limits report complete discovered coverage and distinguish parser-invalid entries from valid Runs. On quota, timeout or unreadable store return the existing explicit bounded unavailable/partial diagnostic state with honest coverage; never render an empty successful overview or exact totals for unobserved files. Existing inventory missing/invalid-store states remain distinguishable from an empty Run directory.

Active and History apply lifecycle grouping to the shared result. Invalid entries remain accounted for by the inventory's existing findings and explicit unclear/blocked presentation; they do not receive fabricated lifecycle or completion. Within each group retain the inventory's attention, known last-activity descending and deterministic Run-ID order. Filter the selected area by the displayed inventory title, exact/partial Run ID and localized attention/status text. Counts distinguish the area's unfiltered total, displayed matches and invalid/unavailable coverage. No result uses filesystem modification time as activity. Labels disclose stored revision, source and title fallback. Long titles and missing activity do not change identity. Search/area changes retain usable keyboard/focus behavior and display a recoverable no-match state.

Both Overview and CompactCockpit consume that same projection. Refactor shared row/area helpers around Run entries rather than duplicating business rules. The main list no longer invokes backlog_titles or reads UR headings while scrolling. Legacy title enrichment, if retained, stays confined to its existing bounded row-ID batching and cannot alter the Run list or search. Detail may retain its existing richer title source, but always displays the same exact Run ID and revision and cannot change overview ordering or membership.

Opening a row selects its explicit Run ID in the current snapshot/session. Current detail continues to use the existing evaluator, Run work summary, source registration, seal and approval proof. Stored lifecycle and recorded approvals remain visibly distinct from current confirmation. Remove the automatic backlog comparison read from ordinary detail; a missing or corrupt legacy file must not make detail fail. Optional historical comparison belongs only to the explicit legacy context and remains non-authorizing. Existing evaluation-out-of-scope behavior is preserved for registered sources beyond the supported read scope.

On change detection the surface shows stale state and invalidates actionable selectors. Reload captures a fresh scope; retry uses existing retryability, and reconnect retires obsolete session IDs. A Run removed while selected returns a clear removed-Run notice and a fresh Run overview, not a neighbor or legacy row. Malformed/unreadable selected Runs remain identified with their diagnostic and a safe return. Documents/resources are rebound only through the same exact current Run registration. A failed read never executes a repair. Browser history/back navigation must not reuse superseded resource IDs. No overview, seal label, completion label or selection accepts approval or bypasses a control action.

### Separate legacy scope

Add an explicit `view: legacy` option to overview snapshot routing; omission means Runs. A view option is mutually exclusive with run_id, and unsupported values fail through the bounded request parser. The HTTP adapter and MCP read schema share this choice. Retain run/document/context operations and exact session/snapshot selectors. The UI exposes Legacy backlog as a distinct optional area with its own loading, missing, invalid, stale and retry state. Run overview requests do not read the legacy file, and returning to Runs captures the Run scope again. Each scope has its own snapshot identity rather than merging stale fragments.

Reuse the existing legacy parser to show original row keys, sections, stored values, safe references and source provenance. A legacy row linked to a real Run may offer explicit opening of that Run, followed by ordinary exact selection and current evaluation. A backlog-only planning row remains a legacy row with no invented selectable Run, completion or gate. Unsafe references remain blocked as today. Missing/corrupt legacy data is a local explanation, not a project initialization or delivery blocker. Do not auto-delete, normalize, rewrite, reseal or convert legacy files.

### Mutation and recovery flow

Audit every production caller of run-backlog planning/synchronization: create/UR, ordinary update and internal continuation, artefact/evidence recording, approval, source revision/PRD reopen, and closeout. Route new work through the existing Run-local write/commit owner with `backlog: null`; remove legacy upsert/archive projection from new operation planning. Return an explicit non-projecting outcome where a compatibility result still exposes a backlog field. Do not claim a skipped projection is synchronized. Retire fresh synchronize-backlog behavior and its gate/doctor repair instructions; an old explicit synchronization entry point must produce a read-only no-longer-required result or supported diagnostic, never recreate recurring writes.

Keep expected revision/content checks, operation ID/request digest replay, exact target/source/material binding, approval checks, seals, output snapshots, archive retention, fsync/atomic replacement and the Run revision commit point with their current owners. Material output and source revalidation remain necessary even when backlog summary projection is removed. In particular, remove only summary checks whose sole purpose was to produce the legacy row, not checks protecting registered source evidence or presentation. Preserve additional required locks for actual existing outputs; the prohibition concerns a backlog lock without a backlog responsibility.

New pending transactions have the existing journal version appropriate to their operation with backlog null. Recovery holds the same Run lock, validates the original operation and commits/restores the original Run-local outputs. Do not acquire the backlog lock for null backlog, implicitly synchronize later or reject another Run merely because an independent Run-only journal is pending. Same-Run concurrent writers still serialize or reject stale revisions. These changes must reach both typed commands and supported CLI/service callers, not one adapter.

Preserve decoding of journal versions 1 through 5 and their original optional backlog, archive, OR, outputs and material fields. A pending journal carrying a legacy backlog output is recognized as legacy shared responsibility. New ordinary operations do not silently finish it: they return the existing recovery-required route. Explicit supported recovery reads that journal, acquires the established Run-then-backlog lock order, validates recorded old/current/next bytes and source constraints and completes or rolls back only as the existing commit-point rules permit. A conflicting legacy file stays recovery-required, never last-writer-wins. Do not rewrite an old journal into a new Run-only journal, alter a recorded approval, transfer a receipt or reseal historical Runs. A pending legacy shared transaction elsewhere is diagnosed before a new conflicting mutation; migration quiescence prevents another old writer appearing during this check. This is the narrow compatibility exception, not a new normal write path.

### Required-file, setup and relationship propagation

Remove MASTER_BACKLOG from mandatory live project files and gate-check/doctor validity dependencies. Preserve actual Run links, registered source relationships, SoT and Context Graph obligations; `delivery-map.js` must derive control-relevant relationships from those existing authoritative registrations instead of active-backlog pointer tables. Do not drop relationship validation just to eliminate a file read. Report malformed optional legacy vocabulary/pointers only when inspecting legacy data, and never turn them into a Run permission veto. Required Run templates, quality contracts and other existing required controls remain required.

Update canonical initialization/scaffold plans, control README, setup instructions, host/profile projections, payload fixture expectations and affected ownership/architecture references together. Fresh initialization does not seed MASTER_BACKLOG as live required state. Retain the legacy template only as an explicitly optional historical/planning reference if an existing package consumer needs it; it must not appear in live-required-file lists or imply that normal operations maintain it. Existing files remain untouched by initialization/update. Use existing projection/build owners for generated contracts and host assets, not manual divergent copies. Update affected existing Context Graph/SoT entries for Run-scoped control and Cockpit ownership at the normal design/implementation checkpoint.

### Worktree rule and isolation

The sole normative rule in task-target-resolution is: when a new worktree is chosen for an initiative, place it at `<owning-primary-checkout>/.agdf/worktrees/<initiative>/`; use the already assigned worktree for the complete coherent initiative. This does not require a worktree for every trivial task. Git's common-directory/worktree metadata, through the existing repository-context/CLI Git boundary, identifies the owning primary checkout when available. A linked worktree's current cwd is not that owner, and the rule must not nest another `.agdf/worktrees` inside an assigned linked checkout. If the owner cannot be determined, settle the owner explicitly before creation. Reject unsafe initiative paths, unresolved destination collisions or a mistaken checkout association before running Git.

The owning primary checkout must ignore its worktree container before creation. Use a contained `.agdf/worktrees/.gitignore` with an ignore-all rule for its contents, preserving any existing foreign rules, and verify the proposed destination with Git's ignore check. This avoids editing a tracked project-wide file for each initiative. Setup documentation and scaffold guidance describe this small preparatory action; AGDF does not create the worktree or mutate arbitrary ignore files automatically. If a repository already ignores the container, preserve that mechanism and verify it instead of replacing it. Never share or symlink control stores between worktrees. Explicit user-selected alternatives and older existing locations remain supported and are not moved.

Describe one writer per Run as a process rule and reviewers as read-only. Existing canonical target identity is checkout-path based, not an automatic branch/HEAD binding or cross-checkout lock. New linked worktrees do not carry untracked control artefacts from their parent. Before any separately authorized handoff/cleanup, inventory and preserve relevant registered and untracked files. No rule grants permission to switch a checkout, relocate a Run, alter global plugin configuration, reuse external ports or clean another initiative.

## 5. Constraints And Compatibility

Cockpit v2 changes only the bounded Cockpit envelope/resource contract. Set the envelope schema_version to 2 and serve its matching UI at `ui://agdf/cockpit/v2.html` through the existing resource constant/build owner; nested Run/approval/document evidence and governance command schemas retain their existing versions. Pair the HTTP service, MCP worker, schema parser, UI types/transport and built desktop/compact resources in one candidate. New UI rejects unsupported/missing envelope versions and unknown scope kinds with an explicit reconnect/update explanation; it does not silently treat old backlog data as a Run overview. Resource and package tests must verify that the advertised URI and actual bundled bytes agree. Existing old-generation sessions may continue read-only with their old payload until retired; their display is not evidence of v2. No live host reinstall or runtime replacement is implied by this design approval.

There is deliberately no new project-config migration flag: current configuration is language preferences, not a runtime-write lease, and adding a flag would not stop already installed old writers. Persisted Run/journal formats remain readable because existing null-backlog representation is sufficient. A technical lock against arbitrary old binaries is not claimed. Supported cutover is operational and mandatory: identify all writers for the target, stop new writes, inventory pending transactions and preserve the old backlog/registered/untracked control files, complete supported legacy recovery, then switch all intended writing hosts/CLI to the same qualified candidate. Recheck no pending legacy transaction and only then resume writing. Do not mix a backlog-requiring runtime with the new writer in one target. Old read sessions may remain diagnostic, but cannot be used to authorize writes through an old control runtime. Concurrent unrelated targets are outside this cutover and stay untouched.

Rollback before the first new mutation may restore the prior matching runtime/UI pair after retiring new sessions. After new mutations, quiesce writers and settle pending operations with the current supported recovery owner, preserve current Run/artefact/receipt bytes and verify the proposed older runtime's exact compatibility on a disposable copy. The older runtime may resume its own backlog policy only as an explicit coordinated downgrade with its actual required files and approved operator plan; do not synthesize old projection rows, erase new receipts, restore an old Run over new state or silently recreate central backlog requirements. If exact backward eligibility cannot be shown, keep the target read-only and forward-fix with the current owner. This is an honest rollback limit, not a promise of universal downgrade. No upgrade, downgrade or cleanup is executed in this Run without separately applicable authorization.

Keep this Run in `.agdf/worktrees/run-overview-worktree-convention`, branch `agdf/run-overview-worktree-convention`. The unrelated CI worktree, its branch, index, evidence/baselines, processes, runtime installs and workflows are protected. No patch is applied there and no shared configuration is changed to speed this feature. Integrate only after its completed result is known and the feature's affected generators/checks have been reconciled with the exact integration baseline. No commit, push, PR merge or release action follows from SD approval.

## 8. Risks And Open Questions

No material design question remains intentionally open before SD presentation. The choices above are proposed resolutions for this approval, not separate prior approvals. Remaining implementation risks are incomplete caller removal, accidentally weakened source validation, legacy journal recovery drift, missing v2 resource pairing and UI stale-state errors. They have explicit proof groups and retain existing review/QA ownership. The operational restriction against mixed writer versions is necessary because existing configuration is not a write lease; the design does not claim to make an arbitrary old binary safe.

TP still needs concrete task IDs, exact command/scenario mapping, available visible-test environments and the integration-baseline checkpoint after the CI fix. Those are execution/evidence details and cannot change inventory authority, compatibility, recovery policy, cutover or rollback. Discovery of a material contradiction returns to SD or the earlier affected PRD owner; it is not resolved by silently modifying this approved design during implementation.

- Lösung: Die Cockpit-Übersicht liest das vorhandene Run-Inventar. Aktiv und Historie verwenden dieselbe Reihenfolge, Suche und gespeicherte Orientierung; erst das Öffnen eines bestimmten Runs liefert dessen aktuelle Prüfung. Alte Backlog-Inhalte bleiben separat und nur lesbar erreichbar.
- Verantwortung: Run-Dateien, bestehendes Inventar, Gate-Prüfung, Siegel und Transaktionsschreiber behalten ihre Zuständigkeit. Es entstehen weder ein neuer Index noch eine zweite Status- oder Freigabequelle.
- Entscheidungen: Neue Run-Operationen schreiben und sperren das zentrale Backlog nicht mehr. Bestehende Journalformate bleiben erhalten; nur ausdrückliche Wiederherstellung darf eine bereits gespeicherte alte Backlog-Verpflichtung abschließen. Neue Worktrees gehören unter .agdf/worktrees/INITIATIVE/ im zuständigen Hauptcheckout, werden dort ignoriert und für das Vorhaben wiederverwendet. Alte Orte und ausdrückliche Alternativen bleiben möglich.
- Integration: Cockpit-Datenvertrag und passende Oberfläche wechseln gemeinsam auf Version 2; Run- und Freigabeformate bleiben bestehen. Schreibende Laufzeiten müssen koordiniert umgestellt werden. Ein beliebiger alter Schreiber wird technisch nicht durch eine neue Konfigurationsmarke ausgeschlossen. Nach neuen Schreibvorgängen braucht ein Rückwechsel einen nachgewiesenen kompatiblen Wiederherstellungsweg; sonst erfolgt eine Vorwärtskorrektur.
- Offen: Keine materielle Designfrage ist vor dieser Freigabe offen. Der TP konkretisiert Aufgaben, Tests, sichtbare Nachweise und den Abgleich mit dem abgeschlossenen CI-Fix. Dieser bleibt unangetastet. Umsetzung, Browser-/Host-Verifikation und Integration sind noch nicht erfolgt; diese Freigabe erlaubt zunächst nur den TP.
