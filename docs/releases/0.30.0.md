# AGDF 0.30.0 — Ein einfacheres .agdf-Projektmodell

AGDF 0.30.0 bündelt die Änderungen seit dem veröffentlichten **0.20.2**. Der Schwerpunkt
liegt auf weniger gemeinsam gepflegtem Zustand: Der Masterbacklog entfällt, geplante
Anforderungen stehen einzeln und jeder Delivery-Run hält seine eigenen Quellen und Nachweise.
Die jüngsten Verbesserungen für Codex-Initialisierung und Diagnose sind ebenfalls enthalten.

Diese Notes beschreiben den vorbereiteten Quellstand. Sie bestätigen keine Veröffentlichung,
Installation oder native Qualifizierung des 0.30.0-Kandidaten. Der Paketstand in npm und ein
Release-Tag werden im gesonderten [Release-Prozess](../../RELEASE.md) geprüft.

## Was sich gegenüber 0.20.2 ändert

### Der Masterbacklog entfällt

Neue Projekte benötigen keine `MASTER_BACKLOG.md` und keinen gepflegten zentralen Index.
Core leitet den Bestand aus den vorhandenen geplanten URs und Runs ab. Titel, Status,
Reihenfolge und Zähler haben damit dieselben kanonischen Quellen in CLI und Cockpit;
eine zusätzliche Backlog-Liste muss nicht synchron gehalten werden.

### Ein Run hält seine eigenen Unterlagen

Das aktuelle Layout heißt `run-folders-v1`; es unterstützt ausschließlich Runs der Version 4.
Ein Run bündelt seinen Zustand, seine Dokumente, Nachweise und Historie unter
`.agdf/control/runs/<run_id>/`. Geteilte alte Artefaktverzeichnisse und alternative Live-Layouts
werden nicht als zweite aktuelle Quelle fortgeführt.

Die wichtigsten Quellen sind:

| Quelle | Aufgabe |
|---|---|
| `.agdf/control/config.json` | Explizite Projektkonfiguration und aktuelle Layout-Kennung |
| `.agdf/control/planned/<plan_id>/UR.md` | Ein geplanter Bedarf mit Inhalt, Priorität und Quellenidentität |
| `.agdf/control/runs/<run_id>/RUN_STATE.md` | Aktueller Zustand eines konkreten Delivery-Runs |
| `documents/`, `evidence/`, `history/` innerhalb des Runs | Run-eigene Dokumente, Nachweise und unveränderliche Historie |

Die Vereinfachung ändert die menschliche Entscheidungshoheit nicht. Geplante Inhalte,
eine vollständige Anforderung oder ein erfolgreicher Test erteilen keine Gate-Freigabe.

### Anforderungen können vor einem Delivery-Run geplant werden

Geplante URs sind eigenständige Dateien statt Zeilen in einem Masterbacklog. Sie können einen
noch nicht vollständig geklärten Bedarf festhalten. Ein ausdrücklicher Start übergibt die
ausgewählte aktuelle Quelle an genau einen zunächst unfreigegebenen Run; die normale
UR-Prüfung folgt anschließend. Wiederholungen behalten die ursprüngliche Identität.

Core bietet diese Planung ohne zusätzliche Erweiterung. Das optionale **AGDF Planning**-Paket
ergänzt den Dialog für Codex CLI und delegiert Zustandsänderungen an Core. Es führt keinen
zweiten Kontrollbestand oder MCP-Server ein. Siehe [geplante URs](../../plugins/agdf/control/planned-urs.md).

### Aktuelle Runs und historische Bestände bleiben unterscheidbar

Die gemeinsame Übersicht leitet aktive, geplante und beendete Arbeit aus den aktuellen
Quellen ab. Runs können über die vorgesehenen Abschlusswege auch bewusst als ersetzt oder
abgebrochen beendet werden. Das Cockpit bleibt eine lesende Ansicht.

Alte Entwicklungsbestände können über den separaten, ausdrücklich ausgeführten
[Offline-Archivimport](../maintenance/cockpit-archive-import.md) für das Cockpit erhalten werden.
Ein solcher Import erzeugt ein lesbares Archiv, keine aktuellen Freigaben oder aktiven Runs.
Ein Run-internes `history/` und dieses Altbestandsarchiv haben unterschiedliche Aufgaben.

### Codex-Projektaufbau lässt sich genauer prüfen

CLI und Plugin-Validator stellen zusätzliche Core-basierte Lesewege bereit:

```sh
agdf project-state --dir /absolutes/git-projekt --json
agdf operation-status --dir /absolutes/git-projekt --module project.initialize/ORIGINAL_UUID --json
agdf status --surface codex --dir /absolutes/git-projekt --native --json
```

Die ersten beiden Befehle lesen Projektzustand und die ursprüngliche Initialisierungsoperation;
sie initialisieren nichts und erstellen keinen Run. Nach einem unklaren Ergebnis bleibt die
ursprüngliche UUID maßgeblich. Fehlende Quellen beweisen nicht, dass eine frühere Wirkung
niemals stattgefunden hat.

Die Codex-Diagnose unterscheidet registrierte Server, relevante Konfiguration und tatsächlich
beobachtete Werkzeuge. Die native Katalogprüfung wird ausdrücklich angefordert. Vorhandene
Zeitgrenzen und ein aufrufbezogener Start-Override bleiben sichtbar; globale Einstellungen
werden dabei nicht automatisch geändert. Leere Doctor-Bestände und fehlende Run- oder
Dokumentquellen erhalten konkretere Erklärungen.

Die MCP-Anleitung enthält vollständige Beispiele für Lese- und Schreibgruppen, explizite
Zielbindungen und Originaloperationen. Versionierte Defaults ergänzen zulässige Eingaben,
ohne Ziel, Run, Revision oder Freigabe aus einer Vermutung abzuleiten. Die Werkzeuge bleiben
beim bestehenden Core-Modell und seinen jeweiligen Befugnissen.

## Hinweise für bestehende Projekte

**Ein Plugin-Update ist keine Projektmigration.** Nur explizites `run-folders-v1`, Run-Version 4
und die aktuellen Record-Formate sind unterstützt. Fehlende, ältere oder unbekannte Layouts
werden als nicht unterstützt gemeldet und bleiben unverändert. Es gibt keinen automatischen
Konverter, Reset oder Legacy-Fallback für den aktiven Kontrollbestand.

- Bereits aktuelle Projekte benötigen keine erneute Initialisierung allein wegen der Versionsnummer.
- Vor einem Wechsel bestehende Projekte und ihre Nachweise sichern und den tatsächlichen
  Projektzustand mit dem installierten, versionsgleichen Runtime-Leser prüfen.
- Ein nicht unterstütztes Projekt nicht durch Löschen oder Überschreiben von `.agdf` passend machen.
  Der Offline-Archivimport ist ein eigener Wartungsschritt mit Vorschau und bewusster Übernahme;
  seine Grenzen stehen in der [Anleitung](../maintenance/cockpit-archive-import.md).
- Alte Freigaben und archivierte Statusangaben bleiben historische Quellen. Sie werden nicht zu
  aktuellen Freigaben eines neuen Runs umgedeutet.
- Für ein neues Projekt das aktuelle Initialisierungsverfahren verwenden. Installation, Projektaufbau
  und Delivery-Start bleiben getrennte Wirkungen; nach einer Host-Aktualisierung ist eine frische
  Sitzung erforderlich. Siehe [Installation](../../INSTALL.md) und [CLI-Referenz](../../packages/cli/README.md).

## Pakete und Host-Grenzen

`create-agdf`, `@agdf/mcp-server`, `@agdf/cli`, Plugin-Metadaten und Site-Metadaten verwenden
gemeinsam 0.30.0. Die vorhandenen Distributionsprofile und ihre historischen Release-Einträge
bleiben beim bisherigen Vertrag. Eine gemeinsame Versionsnummer macht die Fähigkeiten der
verschiedenen Profile nicht identisch: Der öffentliche OpenAI-Skills-Kandidat enthält weiterhin
keinen AGDF-MCP-Server und keine Runtime-Hooks.

| Oberfläche | Einordnung |
|---|---|
| Codex CLI auf macOS; Claude Code CLI auf Windows | Weiterhin die nativen Qualifizierungsziele; ein Nachweis gilt nur für seinen tatsächlichen Kandidaten und sein geprüftes Host-Tupel |
| Codex Desktop; Claude Desktop | Frühere manuelle Berichte bleiben historisch; daraus folgt keine native 0.30.0-Qualifizierung oder Bestätigung eingebetteter MCP Apps |
| Codex CLI unter Windows/Linux | Außerhalb der nativen Qualifizierungsmatrix; Plattform- und Protokolltests ersetzen diese Qualifizierung nicht |
| GitHub Copilot; OpenCode | Auch für 0.30.0 experimentell; Adapter und automatisierte Regressionstests sind keine nativen Sitzungsnachweise |

Node.js **22 oder neuer** bleibt Voraussetzung. Native Qualifizierung ist freiwillig und keine
Voraussetzung der Paketveröffentlichung; erforderliche Repository-CI, Paket-, Integritäts-,
Versions-, Registry- und Bootstrap-Prüfungen bleiben bestehen.
